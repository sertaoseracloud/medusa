Create `frontend/src/api/ws-client.ts` implementing `createRealtimeClient` exactly as declared in `<interfaces>`, using the browser-native `WebSocket` — this plan set deliberately does NOT install `reconnecting-websocket` (Claude's Discretion in 02-CONTEXT.md resolved here): the reconnect path must re-send the auth handshake and re-subscribe every active topic, which the library does not do, so the library would save no meaningful code while adding an `[ASSUMED]`-provenance, 4-years-stale dependency.

Required behavior:
- URL derivation: take `import.meta.env.VITE_API_URL ?? 'http://localhost:3333'` and replace the leading `http` with `ws` (so `https` becomes `wss`), then append `/realtime`. Never hardcode a host.
- The client keeps a `Set<string>` of desired topics. `subscribe`/`unsubscribe` mutate that set and, when the socket is open AND authenticated, send the corresponding frame immediately; when not, they only mutate the set (the frames are sent after the next `auth_ok`).
- On `open`, send `{ type: 'auth', token: getToken() }` and set status `connecting`. On `auth_ok`, set status `connected`, reset the backoff delay to its initial value, and send a `subscribe` frame for every topic in the desired set (this is what makes reconnection transparent).
- On a `data` frame, call `onData(topic, payload)`. On an `error` frame with code `TOKEN_EXPIRED` or `INVALID_CREDENTIALS`, call `onAuthFailure()` and do not schedule a reconnect for that cause (the caller decides whether to refresh the session or sign out).
- On `close`/`error`, set status `reconnecting` and schedule a reconnect with a hand-rolled exponential backoff: initial 1000 ms, factor 2, cap 15000 ms, ±20% jitter, reset on `auth_ok`. After 6 consecutive failed attempts set status `failed` (this drives the hard-failure banner copy) but KEEP retrying at the capped delay — the user is never left with a permanently dead dashboard.
- `close()` sets a `disposed` flag, clears the pending timer and closes the socket with code 1000; a disposed client never reconnects (this is what React StrictMode double-mount cleanup relies on).
- All timers are stored in refs/closure variables and cleared on dispose — mirror the `refreshTimerRef` + `clearRefreshTimer` pattern from `contexts/auth/index.tsx`.

Write `frontend/tests/realtime-reconnect.test.tsx` against a fake `WebSocket` installed on `globalThis` (a small class capturing `send` calls and exposing helpers to fire `open`/`message`/`close`) plus `vi.useFakeTimers()`. Cover: (1) on `open` the first frame sent is `{"type":"auth"...}` and contains the token from localStorage, and no `subscribe` frame is sent before `auth_ok`; (2) after `auth_ok`, every previously requested topic produces one `subscribe` frame; (3) after a `close`, no reconnect before 1000 ms and one after, and the second consecutive failure waits roughly double (assert within the jitter band); (4) after reconnect + `auth_ok`, the auth frame is re-sent and all desired topics are re-subscribed automatically; (5) an `error` frame with code `TOKEN_EXPIRED` invokes `onAuthFailure`; (6) after `close()` no further reconnect timer fires.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser localStorage → WS handshake | The access token leaves storage and crosses into a WS frame here |
| server `data` frames → React state → DOM | Untrusted-by-default third-party (Binance) data is rendered here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07 | Information Disclosure | `api/ws-client.ts` URL construction | mitigate | The token is sent only inside the first WS message body, never appended to the connection URL — this is the browser-side half of SEC-06; verified by the acceptance grep showing no token in the URL derivation |
| T-02-08 | Spoofing | reconnect path | mitigate | Every reconnect re-runs the full auth handshake before any `subscribe` frame is sent; the client never assumes a restored socket is still authenticated |
| T-02-09 | Information Disclosure | token freshness on reconnect | mitigate | `getToken` is invoked per connection attempt (not captured once), so a token rotated by Phase 1's silent refresh is used; a rejected token triggers `onAuthFailure` → the existing silent sign-out path, not a retry loop with a dead credential |
| T-02-10 | Tampering | rendering exchange-supplied strings | accept | Ticker fields are rendered as React text nodes (auto-escaped); no `dangerouslySetInnerHTML` anywhere in the dashboard components — low risk, no mitigation beyond React's default escaping |
| T-02-SC | Tampering | npm installs | mitigate | No new npm package is added by this plan — `skeleton` comes from the official shadcn registry as vendored source, and `reconnecting-websocket` is explicitly rejected (no `[ASSUMED]` install) |
</threat_model>

  <action>
Create `exchanges/binance/binance.user-data.ts` exporting `startUserDataStream` as declared in `<interfaces>`. The listenKey endpoints require only the `X-MBX-APIKEY` header (no HMAC signature), so call them with a plain `fetch` against `https://api.binance.com/api/v3/userDataStream` rather than depending on ccxt implicit-method naming. Required behavior:

1. `POST` to obtain the `listenKey`, then open `wss://stream.binance.com:9443/ws/{listenKey}` through the existing `openBinanceStream` helper so the socket inherits the shared 1s→30s jittered backoff.
2. Schedule the keepalive `PUT` on its own `setInterval` of 30 minutes, started the moment the listenKey is issued — NOT tied to socket events. This is 02-RESEARCH.md Pitfall 1: a perfectly healthy socket is still killed server-side at 60 minutes without it, with no symptom until the close fires. Log keepalive failures at `warn` and, on failure, obtain a fresh listenKey and reopen the socket rather than silently continuing on a dead key.
3. On reconnect of the user-data socket, treat the old listenKey as suspect: request a new one before reconnecting instead of reusing the old string indefinitely.
4. `close()` must clear the interval, `DELETE` the listenKey (best-effort, failures logged at `debug`) and dispose the socket — the interval must never outlive the handle.
5. Normalize `outboundAccountPosition` events into `NormalizedBalance[]` (`B[].a`→`asset`, `B[].f`→`free`, `B[].l`→`locked`, values kept as strings) and pass them to `onBalances`. Ignore other event types (`executionReport`, `balanceUpdate`, `listStatus`) in this phase — they belong to later phases, not this one.
6. Never log, stringify, or attach the API key/secret to any error or message; the key travels only in the `X-MBX-APIKEY` request header.

Add `subscribeUserData(creds, onBalances)` to `IExchangeAdapter` and implement it on `BinanceAdapter` by delegating to `startUserDataStream`.

Write `backend/tests/exchanges/binance-user-data.test.ts` with `vi.mock('ws')`, a stubbed global `fetch`, and `vi.useFakeTimers()`. Cover: (1) starting the stream POSTs once with the `X-MBX-APIKEY` header and opens the socket at the returned listenKey path; (2) advancing 30 minutes fires exactly one keepalive PUT carrying the listenKey, and advancing 60 minutes fires two; (3) `handle.close()` clears the interval — no further PUT after advancing another hour — and issues the DELETE; (4) an `outboundAccountPosition` event produces the normalized balances array with string values preserved; (5) a non-balance event type invokes nothing; (6) no test assertion output or logged object ever contains the fake secret key value (assert the logger spy's serialized calls do not include it).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| encrypted settings row → decrypted credentials in memory | AES-256-GCM sealed keys are opened here for outbound Binance calls |
| `account:{userId}` topic → a specific browser socket | Private financial data crosses to exactly one authenticated user |
| backend → `api.binance.com` listenKey endpoints | The API key leaves the process in a request header |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03b | Information Disclosure | `account:` subscribe path | mitigate | The Plan 02-01 ownership check (topic `userId` must equal the authenticated `state.userId`, else close 4003) runs BEFORE any credential lookup; a test asserts the settings repository is never touched on a rejected cross-user subscribe — ASVS V4 |
| T-02-18 | Information Disclosure | decrypted credentials | mitigate | `get-exchange-credentials.use-case.ts` is server-only, is never registered on a route, and is grep-verified absent from `infrastructure/` and `app.ts`; the masked `toSettingsDto` remains the only settings serialization boundary — ASVS V2/V6 reuse of Phase 1 crypto, no new primitives |
| T-02-19 | Information Disclosure | logs | mitigate | The API key travels only in the `X-MBX-APIKEY` header; no credential value is passed to pino (which already redacts `accessKey`/`secretKey` paths from Phase 1), asserted by a test that inspects serialized logger calls |
| T-02-20 | Denial of Service | listenKey expiry | mitigate | Independent 30-minute keepalive interval (not tied to socket events), fresh listenKey on reconnect, and interval cleared in `close()` so it cannot leak — 02-RESEARCH.md Pitfall 1 |
| T-02-21 | Spoofing | stream/user binding | mitigate | The supervisor derives credentials strictly from the topic's `userId`, which the gateway has already proven equals the authenticated user; a defensive assertion in `ws-server.ts` prevents a future refactor from decoupling them |
| T-02-SC | Tampering | npm installs | accept | Only the official shadcn `scroll-area` component is added; listenKey calls use the platform `fetch`, adding no HTTP client dependency |
</threat_model>

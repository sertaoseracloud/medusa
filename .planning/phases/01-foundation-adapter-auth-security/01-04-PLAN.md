<objective>
Build the two security-critical primitives the credentials slice depends on: an AES-256-GCM credential vault and the `IExchangeAdapter` abstraction with its ccxt-backed Binance implementation.

Purpose: This is the backend half of the "operator saves Binance credentials" slice (completed by Plan 05, which exposes the endpoint and UI-facing DTO). Output: `security/crypto.ts`, `security/credential-vault.ts`, `exchanges/core/*`, `exchanges/binance/binance.adapter.ts`, two green unit test files.
</objective>

    `security/crypto.ts`: implement `encrypt(plaintext: string, masterKey: Buffer)` returning `{ nonce, ciphertext, authTag }` and `decrypt(nonce, ciphertext, authTag, masterKey)` using Node's built-in `node:crypto` with algorithm `aes-256-gcm`, exactly as RESEARCH.md Pattern 2 shows. The nonce is `randomBytes(12)` generated inside `encrypt` on every call — it must not be a parameter, a module constant, or derived from a user id, counter, or timestamp. Do not write any cipher logic of your own beyond calling `createCipheriv`/`createDecipheriv`; do not use the `aes-js` package the legacy code used.

    `security/credential-vault.ts`:
    - `sealCredential(plaintext, masterKey)` → `'v1:' + base64(nonce ‖ ciphertext ‖ authTag)`. The `v1:` prefix is the key/format version that makes future key rotation possible (RESEARCH.md Pattern 2 "include a version byte"); the `settings.key_version` column added in Plan 05 mirrors it.
    - `openCredential(sealed, masterKey)` → parses the version prefix (throwing a clear error for an unknown version), splits the buffer into the 12-byte nonce, the trailing 16-byte auth tag, and the ciphertext between them, and returns the plaintext. A failed auth-tag check must propagate as a thrown error, never a silently truncated string.
    - `maskSecret(plaintext)` → twelve `•` characters followed by the last 4 characters of the input (D-05 / UI-SPEC masking row); inputs shorter than 4 characters return only the mask characters.
    This module must never log its inputs or outputs, and must never be imported by a controller directly — Plan 05's use case is its only caller.

    `tests/security/credential-vault.test.ts` (unit, no DB): sealing the same plaintext twice with the same key yields two different strings (nonce uniqueness) that both open back to the original; `openCredential` on a ciphertext with a single flipped byte throws; `openCredential` with a different 32-byte key throws; `sealCredential` output starts with `v1:`; the decoded payload is at least 28 bytes (12 nonce + 16 tag) longer than nothing and its first 12 bytes differ between two seals of the same input; `maskSecret('ABCDEFGH1234ab12')` returns a string ending in `ab12` that does not contain `ABCDEFGH`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend process → Binance REST API | Outbound credentialed calls cross here; responses and errors are untrusted input |
| Backend process → encrypted-at-rest storage | Plaintext credentials exist only inside this process, never beyond the vault boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-SEC01 | Tampering / Information Disclosure | `security/crypto.ts` nonce generation | mitigate | `randomBytes(12)` inside `encrypt` on every call, asserted by the two-seals-differ test; deterministic derivation is blocked by an acceptance-criteria grep (RESEARCH.md Pitfall 1) |
| T-01-GCMTAMPER | Tampering | Sealed credential strings in the database | mitigate | AES-GCM auth tag verified on every open; a flipped byte throws instead of yielding plaintext (tested) |
| T-01-KEYROT | Tampering | Ciphertext format | mitigate | `v1:` version prefix plus the `key_version` column in Plan 05 make a future re-encryption pass possible without ambiguity |
| T-01-CREDLOG | Information Disclosure | Vault and adapter code paths | mitigate | No logging statements inside `credential-vault.ts`; the adapter never logs `creds`; pino `redact` from Plan 01 covers `accessKey`/`secretKey` keys anywhere in a log object |
| T-01-EXCHERR | Information Disclosure / Repudiation | ccxt error handling | mitigate | Errors are mapped by class to four distinct domain errors (D-07); raw ccxt error objects, which can echo request parameters, never reach a response body — the central handler only emits `DomainError.message` |
| T-01-RLDRIFT | Denial of Service | Binance rate limits | mitigate | One memoized ccxt instance per credential fingerprint with `enableRateLimit: true` preserves the client-side limiter state instead of resetting it per request |
</threat_model>

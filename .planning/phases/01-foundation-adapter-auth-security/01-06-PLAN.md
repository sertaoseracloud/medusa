<objective>
Make the session real: silent background refresh, rotation on every refresh, logout that actually revokes server-side, and an operator password-change screen path.

Purpose: SEC-02, SEC-03 and AUTH-03. The legacy system's logout pushed the token into an in-memory array that nothing ever read — a complete no-op. The fix is not "create a table" (Plan 01 did that) but "make the check load-bearing on every refresh call", which is exactly the failure mode RESEARCH.md Pitfall 2 warns gets skipped when the table and its enforcement land in different steps.
Output: refresh/logout/change-password use cases and routes, frontend silent-refresh timer and revoking sign-out, three green test files.
</objective>

    `application/refresh.use-case.ts`: `createRefreshUseCase({ refreshTokens, users, signAccessToken })` with `execute({ refreshToken })`. Flow: `hash = hashRefreshToken(refreshToken)` → `findActive(hash)`; when it is null or `isValid(hash)` is false, throw `TokenRevokedError` (never fall through to issuing a token — this is the exact legacy defect) → rotate: insert a new refresh token row for the same user with a fresh `expiresAt`, then `revoke(hash)` on the old one, both inside a single `db.transaction` so a crash cannot leave the operator with two live tokens or none → sign a new 15-minute access token → return both. Rotation on every refresh is the RESEARCH.md Open Question 1 recommendation and sits inside the D-12 discretion band.

    Add `refreshBodySchema` = `{ refreshToken: z.string().min(1) }` to `auth.schemas.ts` and register `POST /auth/refresh` in `auth.routes.ts`. The route is unauthenticated (the access token may already be expired — that is the point) but carries `config: { rateLimit: { max: 30, timeWindow: '15 minutes' } }` so a stolen-token brute force cannot be run at the global 100/min budget.

    `tests/auth/refresh.test.ts`: login, then refresh → 200 with a different `accessToken` and a different `refreshToken` than the originals; the new access token works on `GET /auth/me`; replaying the ORIGINAL refresh token after rotation → 401 and no new row inserted; a refresh token that was never issued → 401; a row manually aged so `expires_at` is in the past → 401; assert the `refresh_tokens` row count after one rotation is 2 with exactly one having `revoked_at` null. Also assert that an access token minted in the test with `exp` in the past is rejected by `GET /auth/me` but that `POST /auth/refresh` still succeeds for a valid refresh token — proving the 15-minute access lifetime does not end the session (SEC-02).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /auth/refresh` | An unauthenticated endpoint that mints access tokens; the highest-value unauthenticated surface in the system |
| Browser → `POST /auth/logout` / `PATCH /auth/password` | Authenticated session-state mutations |
| Backend → `refresh_tokens` table | The authoritative session store |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-SEC03 | Spoofing / Repudiation | Refresh-token replay after logout | mitigate | `revoked_at` is set on logout and checked by `findActive`/`isValid` on every `/auth/refresh` call; `tests/auth/logout.test.ts` asserts the post-logout refresh returns 401 (RESEARCH.md Pitfall 2 — the check, not the table, is the fix) |
| T-01-SEC02 | Spoofing | Long-lived credential exposure | mitigate | 15-minute access tokens with a 14-day refresh token rotated on every use, so a leaked refresh token is invalidated the moment the legitimate client next refreshes |
| T-01-REPLAY | Spoofing | Rotated refresh token reuse | mitigate | Rotation revokes the presented token inside the same transaction that issues its replacement; replay of the old value returns 401 (tested) |
| T-01-RTBRUTE | Denial of Service / Spoofing | `POST /auth/refresh` guessing | mitigate | Per-route `rateLimit { max: 30, timeWindow: '15 minutes' }` on top of the global limit; tokens are 48 random bytes, so guessing is infeasible regardless |
| T-01-PWCHANGE | Elevation of Privilege | `PATCH /auth/password` | mitigate | Requires a valid access token AND the current password; all refresh tokens for the user are revoked on success so a stolen session cannot outlive the change |
| T-01-REFRESHLOOP | Denial of Service | Frontend 401 interceptor | mitigate | A single shared in-flight refresh promise, one replay per request, and an explicit exclusion of `/auth/refresh` from retry prevent a self-inflicted request storm |
| T-01-PWREVERT | Repudiation | Password reverting on restart (D-03) | accept | Documented behaviour of the env-var-seeded single-operator model; the operator is warned in the UI (D-04) and in the route comment. Revisit only if multi-user provisioning is ever introduced (v2) |
</threat_model>
